# Acoustic ownership and double-talk: feasibility contract

Status: **architecture recommendation, not an implemented AEC feature** (2026-09-30). The [physical beta evidence](POST_0.2.3_BETA_PLAN.md) and current runtime establish the need. This document specifies a falsifiable next step; it does not claim that any processor works on Sam's devices.

The first [offline Windows AEC3 probe](AEC_PROTOTYPE_2026-09-30.md) runs through
an optional native binding but **fails the declared separation gate**. No runtime
integration or early barge-in was attempted. Its measured 8 ms signal latency
is distinct from echo-path delay. Keep the preferred upstream APM contract and
conservative production fallback until a processor passes the same fixtures.

## Current boundary and limitation

`SoundDeviceCapture.frames` opens a `sounddevice.RawInputStream` with a blocking read of 20 ms, default 16 kHz mono PCM16 (320 samples, 640 bytes). Each immutable `AudioFrame` gets a Python monotonic timestamp **after** the read, a sequence number and gain in the range 0–2. Capture overflow is an error, not silently dropped speech. The same gained frame reaches WebRTC VAD (10/20/30 ms accepted; three activation and four release frames by default), the bounded STT stream, and `voice.level`. Ordinary voice capture retains ten frames of pre-roll. The separate playback-time interruption monitor starts a candidate STT stream on VAD evidence, screens partial/final text against a pinned delivery generation, and never promotes an unverified candidate merely because TTS ends. It has no acoustic human-origin signal and no dedicated pre-roll across candidate creation.

System Speech synthesizes one bounded WAV at 16 kHz mono PCM16; the eSpeak fallback uses 22.05 kHz mono PCM16. `SamRuntime._metered_tts_frames` applies output gain (0–2) to each yielded PCM frame, publishes `tts.level` from that frame, and yields **that actual post-gain PCM** to `SoundDeviceOutput.play`. Output uses a separate `RawOutputStream`, with `blocksize=0`, sequential writes and cancellation that aborts/closes the stream. TTS frames are nominally 20 ms. Output underflow is counted. Input and output use independent PortAudio streams and do not expose hardware capture/render timestamps, a shared sample clock, output latency or a render loopback reference. Current Python monotonic frame times describe application handling, not when a sample crossed the device. The `tts.level` and `voice.level` protocol events are lossy activity measurements, not acoustic samples or alignment information.

Thus VAD energy and transcript similarity cannot prove near-end human speech during playback. Text screening protects commitment after STT but arrives too late for prompt interruption. A simple amplitude ratio, correlation threshold or fixed-duration VAD timer is not a safe replacement. The target is a sustained *human-origin* decision in roughly one second when evidence is clear, without making one second an unconditional timer.

## Candidates considered

| Candidate | Fit and cost | Decision |
| --- | --- | --- |
| **WebRTC Audio Processing / AEC3** | Its API explicitly accepts near-end `ProcessStream`, far-end `ProcessReverseStream`, a stream-delay estimate and approximately 10 ms frames. Native int16 rates include 16/32/48 kHz; the int16 capture and reverse rates must match. Its BSD-style license is compatible in principle, subject to final binary/dependency license review. Sam would need a maintained, version-pinned native binding or small native shim, resampling, delay estimation and native packaging. Full upstream WebRTC is a substantial build/binary burden; an unreviewed Python wheel is not a selection. | **Preferred processor interface and first feasibility prototype.** Do not add a dependency until binding provenance, license, Windows wheels/build and size are established. |
| **Windows Voice Capture DSP / device APO** | Microsoft's `CLSID_CWMAudioAEC` Voice Capture DMO offers AEC in filter mode (application supplies microphone and speaker-line PCM) or source mode (the DMO owns capture and synchronization). Filter mode still needs Sam to solve alignment and a COM/DMO adapter; source mode replaces Sam's current PortAudio capture ownership. Windows 11 AEC APOs can receive OS-managed render reference and timestamps, but are device/driver components, not a general WASAPI switch Sam can enable for all devices. Device effects may be present but are not guaranteed or under Sam's control. | **Fallback investigation for supported Windows devices**, especially if WebRTC packaging is disproportionate. Do not call generic WASAPI or a device enhancement a portable Sam AEC solution. |
| **SpeexDSP echo canceller** | Mature BSD-style C API with explicit playback and capture frames (typically 10–20 ms); its playback/capture helper assumes a two-frame delay. A Sam binding and actual delay treatment are still required; echo cancellation alone does not prove near-end double-talk. | Plausible lighter fallback if the preferred route fails packaging or measured double-talk tests. No dependency is selected now. |

The existing `webrtcvad-wheels` package is only VAD. It does **not** provide WebRTC AEC3. The Windows platform may already apply device AEC, so an eventual Sam processor must avoid claiming double cancellation is harmless without device-specific evidence.

## Preferred integration contract

1. Place one replaceable, generation-scoped **acoustic processor** between raw/gained capture and playback-time VAD/STT, while keeping the current capture, STT, turn, delivery and cancellation owners. Feed the exact post-gain bytes sent to output as a bounded reverse/render stream. Feed microphone PCM as the near-end stream. Preserve raw input only in a short bounded pre-roll/alignment buffer; do not log or persist either waveform by default.
2. Normalize both streams to 16 kHz mono PCM16 in 10 ms processor frames. Split existing 20 ms capture/TTS chunks; resample 22.05 kHz eSpeak output before reverse processing. A future binding may choose float internally, but the external Sam boundary remains explicit. Preserve frame sequence, delivery generation and source timing metadata through conversion.
3. The playback owner supplies render frames at the output-write boundary. A bounded reference ring holds enough history for output-device latency and room echo, keyed to delivery/generation. The capture owner supplies near-end frames. A synchronization layer must estimate or obtain render/capture device delay, account for buffering and drift, and call the processor's delay API. Python `monotonic_ms` alone is not a hardware delay measurement. If the delay cannot be established within a validated range or the reference overflows/underflows, report **acoustic ownership unavailable** and retain today's conservative transcript-gated behavior.
4. Use echo-processed near-end frames for playback-time VAD and candidate STT only after tests show intelligibility is preserved. Early cancellation requires sustained speech evidence from this near-end path **and** a processor/decision state that is valid for the current reference and delay. AEC residual/VAD is evidence, not an infallible speaker ID: echo-only, double-talk and changing-delay false positives must be measured. Do not make a global raw-RMS threshold or a transcript match the early trigger.
5. Keep a bounded pre-roll from before candidate activation and send it once to the candidate STT stream. Candidate identity retains the pinned playback generation/reference metadata through playback completion and late STT finalization. On accepted human-origin speech, stop **delivery only**, keep the full assistant text, continue the same captured utterance through STT and `turn.committed`. On ambiguous or failed processing, stay provisional and use the existing conservative path; never auto-promote on TTS completion.
6. Processor, resampler, reference ring and delay state belong to the playback/listening overlap, not a mutable active-generation pointer. Cancellation, device change, stream restart and format change retire/reset them idempotently. Late frames/events from a retired identity cannot influence a new candidate. Input/output `voice.level` and `tts.level` remain separate measurements; no shader or conversation protocol redesign is implied.

## Smallest falsifying prototype and current result

The isolated optional adapter and signal fixtures now exist; see the probe result above. It did not pass, so production alignment, 22.05 → 16 kHz output conversion and ownership/decision integration remain deferred. A later upstream adapter must replay the same declared cases before routing live Sam turns or adding UI controls. Verify its source/license, Windows build path, binary size and 10 ms frame/delay API. Retain playback-only leakage; delayed and attenuated leakage; leakage plus background noise; independent human-like speech over playback; speech starting just before playback ends; changing delay; cancellation/reset and a subsequent clean operation.

**Pass:** echo-only fixtures never become confirmed user speech or stop playback; independent overlapping speech is preserved as intelligible near-end PCM with its onset/pre-roll and can produce a timely sustained decision before final STT; changing delay and reset do not contaminate a later operation; all buffers are bounded and no stale identity can commit. Measure elapsed simulated capture duration from onset to decision; the clear double-talk case should permit a decision around the one-second product target, not require end-of-utterance STT. Record processor latency and package cost. **Fail/stop:** false interruption, lost near-end onset, unbounded buffering, unstable delay handling, excessive native/build cost or incompatible licensing. Deterministic success is only a feasibility gate; one later bounded physical speaker/microphone check across representative devices is needed before claiming real acoustic reliability.

## Open risks and primary sources

Render-write time can precede acoustic output; capture-read time follows hardware capture. Device latency, resampling drift, room echo, speaker volume, headset behavior, OS enhancements and double-talk may defeat a desktop fixture. The WebRTC API does not promise a ready-made human/speaker identity verdict; the prototype must validate the combined decision. No robust maintained Python binding was selected by this review.
